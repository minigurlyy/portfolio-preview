02 · The problem

Luxury runs on trust. Size charts don't build it.

I audited how luxury and occasion-wear sites sell high-cost pieces. Beautiful imagery everywhere, and almost nothing to help a shopper picture the piece on their own body. Tap the numbers to see each finding.

  • Static imagery only. Product pages lead with model photography on one body type.
  • Fit is a link, not a feature. Sizing hides behind a small "size guide" link next to the add-to-cart button.
  • Trust is borrowed. Press logos and celebrity features stand in for confidence about fit.
The question I designed around How might we help a shopper feel personally seen before they buy a piece made to be worn once, perfectly?
AIAI in the loop · ResearchChatGPT
The ask

Summarise how luxury sites handle fit and sizing online, and where shoppers lose confidence.

What it gave me

A fast first map of competitors and common fit tools, which I used as a checklist for my own audit.

My call

I verified every claim on the live sites myself and only kept patterns I could screenshot.

05 · Experience ii · Body scan

A fitting room in two photos.

The scan had to feel like a fitting appointment, not a form.

Gender, then height and weight, then a front and a side photo. My backend sends the photos to 3DLOOK's Mobile Tailor API and returns chest, waist, hip, shoulder, inseam and sleeve.

The capture and measurement technology is 3DLOOK's. The flow, the interface and the integration are mine.

Testing without real bodies

Instead of anyone's private photos, I generated synthetic subjects in the pose the API expects, then checked the measurements and avatar that came back.

AIAI in the loop · BackendCodex
The ask

Build a server-only Next.js route that takes the wizard's form data and photos, creates a 3DLOOK person, polls the task, and returns six measurements.

What it gave me

A working route scaffold: form parsing, the 3DLOOK create-upload-poll sequence, and CORS for the Framer front end.

My call

I designed the request contract, validated every field, capped polling at 30 tries, and mapped 3DLOOK's fields to the six measurements a fitting needs.

06 · Experience iii · 3D fit

Turn it. Read the drape.

Photos show how a dress looks on a model. 3D shows how it moves. I built garments in CLO3D, explored Sketchfab-style viewers, model-viewer and AR Quick Look, and brought interactive pieces into the product pages.

AIAI in the loop · Visual developmentChatGPT image
The ask

Variations on a structured purple evening gown on dress forms, studio lighting, couture detailing.

What it gave me

Fast concept imagery to test how a collection would read on black before committing to 3D builds.

My call

07 · The build

Designed in Framer. Engineered past it.

Framer got me to a real, responsive site fast. Where it stopped, I wrote code: React/TSX overrides for the scan wizard and 3D viewers, and a CMS model that holds every collection, product, image set and price, so new collections drop in without touching layout.

AIAI in the loop · Front-end codeChatGPT
The ask

Fix my SketchfabViewer component so the modelId prop updates the viewer, and show me how to pass a different model per product.

What it gave me

A corrected React component that re-initialises whenever the model ID changes.

My call

I wired the model ID to the CMS so each product loads its own 3D model, then tested every product page.

08 · Key decisions

Three calls that shaped it.

Each one traded something away. These are the choices I would defend in a critique.

Decision 01 · Scan technology

Partner for the scan, own the experience.

Options
Build my own pose-and-measure model, fake it with manual inputs, or integrate a proven body-scan API.
Chose
3DLOOK's Mobile Tailor API, so the measurements are real and my time goes into the flow around them.
Gave up
Control over capture rules and the inputs the API requires.
Decision 02 · Architecture

Framer for speed, a server for secrets.

Options
A fully custom front end, or Framer with code where it falls short.
Chose
Framer with React overrides and a CMS, plus one small Next.js route, because browser code can't hold an API key.
Gave up
A single codebase. Two deploys to keep in sync instead of one.
Decision 03 · Friction vs. accuracy

Ask for weight, but make it painless.

Options
Skip weight for a shorter form, or ask for it because 3DLOOK's person-first flow requires it.
Chose
Keep it, as a dial in pounds that converts to kilograms on the server, one question per screen.
Gave up
One extra step in a flow where every step costs completion.

Principle 01

Secrets stay server-side. No API key in Framer or browser code. Only the backend talks to 3DLOOK.

Principle 02

AI output is a starting point. A lead to verify, a scaffold to harden, or a concept to curate, never the final answer.

10 · Outcome

From concept to a working product.

Live and working

A real body-scan integration, not a mock-up, running on a public site.

A foundation, not a feature

Body data becomes the base for recommendations, avatar previews and, later, made-to-measure orders.

What I'd do differently

Put the scan in front of real shoppers earlier, and plan the product-to-3D pipeline from the catalogue up instead of piece by piece.

What I'd do next

Fit the shopper's own avatar into the 3D garment, and test the scan flow with real shoppers for drop-off and trust.
